Scénarios Détaillés de Communication API

Scénario 1 : Créer une Commande (Flow Complet)

1. Client Request (POST /api/orders) → Payload: { userId: 1, items: [...] } 2. API Gateway → Proxy request vers Order Service (:3003) 3. Order Service : - Valide le payload et calcule le montant total (total_amount) - Insère la commande dans PostgreSQL - Publie l'événement "order.created" sur RabbitMQ (Topic Exchange: orders) 4. RabbitMQ route le message vers la file du Notification Service 5. Notification Service : - Consomme le message asynchrone - Requête la DB pour les infos utilisateur (email) et cache Redis pour produits - Envoie l'email de confirmation via SMTP (MailHog) 6. Réponse immédiate au client (201 Created) sans attendre l'envoi d'email. Temps total de la requête API : ~60ms.

Scénario 2 : Lister le Catalogue Produits (Cache-Aside Pattern)

1. Client Request (GET /api/products) 2. API Gateway → Proxy request vers Product Service (:3001) 3. Product Service : - Vérifie le cache Redis (clé "products:all") - Si HIT (trouvé) : retourne immédiatement les données (Temps : ~15ms) - Si MISS (non trouvé) : * Requête la base PostgreSQL * Sérialise et stocke dans Redis avec un TTL (ex: 3600s) * Retourne la réponse (Temps : ~110ms) Hit rate espéré : ~80%. Permet de réduire la charge DB massivement.

Modèle de Données

Structure des tables PostgreSQL et relations entre les entités.

👥 Table: users
  • id (PK, UUID)
  • email (VARCHAR, UNIQUE)
  • password_hash (VARCHAR)
  • name (VARCHAR)
  • created_at (TIMESTAMP)
  • updated_at (TIMESTAMP)
📦 Table: products
  • id (PK, UUID)
  • name (VARCHAR)
  • description (TEXT)
  • price (DECIMAL)
  • stock (INTEGER)
  • created_at (TIMESTAMP)
  • updated_at (TIMESTAMP)
🛒 Table: orders
  • id (PK, UUID)
  • user_id (FK → users.id)
  • total_amount (DECIMAL)
  • status (VARCHAR) [pending, completed, failed]
  • created_at (TIMESTAMP)
  • updated_at (TIMESTAMP)

Architecture Microservices

Bien que les données soient présentées ensemble ici, dans un contexte de microservices stricts, chaque service gèrerait idéalement sa propre base de données. Actuellement, la plateforme partage une instance PostgreSQL avec des schémas logiques séparés.

Contexte Métier et Technique

Cette application n'est pas qu'un simple site e-commerce. Il s'agit d'une Plateforme d'Apprentissage DevOps conçue pour démontrer les architectures modernes basées sur les microservices, la conteneurisation et l'orchestration. Elle permet de gérer des produits, des utilisateurs, des commandes et des notifications, tout en appliquant des standards stricts de sécurité et de scalabilité.

Playbook de Réponse aux Incidents (Incident Response)
🔴 Niveau 1 : Indisponibilité API

Action immédiate : Vérifier les logs de l'API Gateway et le statut des pods Kubernetes. Redémarrer l'ingress si nécessaire.

🟠 Niveau 2 : Lenteur Base de données

Action immédiate : Analyser le pool de connexion (pg_stat_activity). Tuer les requêtes longues (idle in transaction). Vérifier l'usage CPU/RAM du nœud Postgres.

🔵 Niveau 3 : File d'attente pleine

Action immédiate : RabbitMQ alerte si la queue dépasse 1000 messages. Vérifier si le Notification Service a crashé ou s'il est bloqué (timeout SMTP).

JWT tokens expiration 24h, refresh tokens, bcrypt pour les passwords, gestion des rôles.

🛡️ Transport & Réseau

HTTPS/TLS en production, SSL obligatoire sur les connexions DB, CORS whitelist domaines.

100 req/min par utilisateur via Redis + middleware. Protège contre les abus et DDoS applicatifs.

Variables d'environnement pour les secrets. Utiliser Vault ou K8s Secrets en production.

Résilience : Tolérance aux Pannes (Failure Scenarios)
🔴 Scénario : PostgreSQL Down

Impact : Services métiers (Product, Order, User) incapables de lire/écrire. L'API Gateway reste up mais renvoie des erreurs 500/503.

Recouvrement : Les services implémentent un retry avec backoff exponentiel. Dès restauration de la DB, les connexions au pool se rétablissent automatiquement.

🟠 Scénario : RabbitMQ Down

Impact : Les appels API synchrones continuent de fonctionner. Les événements de commandes (Order Notifications) sont ralentis ou mis en file d'attente locale.

Recouvrement : L'Order Service retente la connexion. À la reconnexion, les messages en attente sont publiés et traités par le Notification Service.

🔵 Scénario : Redis Down

Impact : Les Cache Misses grimpent à 100%, reportant la charge sur PostgreSQL (performances dégradées 5-10x). Pas de perte de données persistantes.

Recouvrement : À la relance de Redis, le cache se repeuple progressivement (Cache-Aside pattern) et les temps de réponse se normalisent.
